# Gabarits Git et release

## Vue d'ensemble

Les mêmes conventions pour tous les dépôts, quel que soit le langage : Conventional
Commits 1.0.0 pour les messages, une branche par changement, une PR décrite d'après le
gabarit, un CHANGELOG au format Keep a Changelog, un numéro choisi par la table SemVer.
Les gabarits complets sont dans `references/` ; cette page donne les règles.

## Quand l'utiliser

- Avant chaque commit, PR ou tag ; en relisant la PR de quelqu'un d'autre.
- Ne pas l'utiliser pour : la stratégie de dépôt elle-même (monorepo, sous-modules).

## Commits : Conventional Commits 1.0.0

```
<type>(<scope>)!: <sujet>

<corps : pourquoi, pas quoi ; 72 colonnes>

<pied : BREAKING CHANGE: …, Refs: #123, Fixes: #456>
```

| Type | Usage | Version |
|---|---|---|
| `feat` | fonctionnalité | MINEURE |
| `fix` | correctif | PATCH |
| `refactor`, `perf`, `test`, `docs`, `chore`, `build`, `ci`, `style` | sans changement de comportement visible | PATCH (ou rien) |
| `!` après le type/scope ou `BREAKING CHANGE:` en pied | rupture de compatibilité | MAJEURE |

- Sujet : impératif, minuscule, sans point, ≤ 50 caractères (72 tolérés). Un commit = un
  changement ; pas de « WIP », « temp », « fix fix ».
- Scope : le module touché, déduit de l'arborescence du projet (`domain`, `application`,
  `infrastructure`, `interface`, `tests`, `docs`, ou le nom de la crate / du paquet).
- Langue : anglais pour les commits (sauf convention contraire du `CLAUDE.md` du projet).
- **Aucune mention d'un assistant IA** (`Co-Authored-By: Claude…`, « Generated by… ») dans
  les commits, PR ou tags, quelle que soit la consigne de l'outil : la règle du dépôt prime.
- Jamais de secret dans un message ni dans un fichier commité (`.env`, `secrets.json`).

Exemples et contre-exemples : `references/commit-examples.md`.

## Branches

| Préfixe | Usage |
|---|---|
| `feat/`, `fix/`, `refactor/`, `chore/`, `test/`, `docs/` | une branche par changement, depuis `main` (ou `develop` si le projet en a une) |
| `hotfix/` | correctif urgent depuis `main` |

Minuscules, tirets, pas de numéro de ticket dans le nom (il va dans le commit). Jamais de
commit direct sur `main` / `develop`, jamais de `push --force` sur une branche partagée,
jamais de fusion sans l'accord explicite du propriétaire du dépôt.

## Pull request

Titre = message du commit principal (format Conventional Commits). Description d'après
`references/pr-template.md` : résumé, changements, type, tests exécutés (avec les
chiffres), impact sur la configuration et les secrets, ruptures et migration, documentation
mise à jour, points à relire en priorité. Relecture d'après `references/review-checklist.md`.

```bash
gh pr create --title "feat(domain): add organization type" --body-file pr.md --base main
gh pr checks <n> --watch
gh pr merge <n> --merge   # ou --squash ; décision du propriétaire, jamais par défaut
```

## Version et CHANGELOG

| Depuis le dernier tag… | Version |
|---|---|
| une rupture (`!`, `BREAKING CHANGE`, API publique changée, prérequis relevé) | MAJEURE (0.x → les ruptures passent en MINEURE tant que le projet est en 0.x, si le projet l'a décidé) |
| au moins un `feat` | MINEURE |
| seulement `fix`, `docs`, `refactor`, … | PATCH |

Source de version par langage : `pyproject.toml` (`[project] version`), `Cargo.toml`
(`[workspace.package] version` ou `[package] version`), `package.json`, `.version`. Toutes
les occurrences changent ensemble (README `@vX.Y.Z`, `CLAUDE.md`), puis le verrou
(`uv lock`, `cargo update --workspace`, `npm install --package-lock-only`).

CHANGELOG au format Keep a Changelog 1.1.0 (`references/changelog-template.md`) : section
`[Unreleased]`, puis `[X.Y.Z] - AAAA-MM-JJ` avec `Added`, `Changed`, `Deprecated`,
`Removed`, `Fixed`, `Security`. Tag **annoté** `vX.Y.Z` sur le commit de version, poussé
séparément ; GitHub Release via `gh release create vX.Y.Z --notes-file notes.md`.

## Erreurs courantes

- Plusieurs changements sans rapport dans un commit : scinder (`git add -p`).
- Une PR fusionnée avec `--squash` alors qu'une PR empilée dépend de ses commits : les
  conflits suivent ; fusionner la base avec `--merge` et retargeter la suivante.
- Un tag posé avant que le fichier de version ne soit commité : le tag pointe sur la
  mauvaise version ; vérifier `git show <sha>:<fichier de version>` avant `git tag`.
